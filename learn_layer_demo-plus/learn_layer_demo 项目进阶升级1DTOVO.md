learn_layer_demo Plus 版本更新说明（DTO/VO 数据分层改造）
一、版本概述
本版本是基础三层架构项目的进阶升级版本，属于「Handler-Service-Repository 分层架构」知识体系内的规范优化，核心是引入 DTO（数据传输对象）+ VO（视图对象） 实现数据分层，彻底解耦数据库模型与接口协议。
本版本仅围绕分层架构本身做规范升级，不引入 Context、Validator、JWT、Redis 等独立组件，相关组件将作为独立知识点单独学习。
二、为什么引入 DTO/VO（旧版本存在的问题）
基础版本采用「数据库模型 Model 全链路透传」的写法，适合快速上手，但不符合企业级项目规范，存在以下核心问题：
强耦合问题：接口入参、返回值直接绑定数据库表结构，数据库字段一旦调整，接口协议会同步变动，前后端协作成本高。
数据安全风险：数据库全部字段直接暴露给前端，后续新增密码、盐值、内部状态等敏感字段时，极易意外泄露。
入参规范混乱：路径参数、请求体参数多在 Handler 内定义临时结构体，分散难维护，没有统一的入参契约。
扩展能力弱：若接口需要返回计算类字段（如年龄等级、用户标签），只能强行写入 Model 或在 Handler 中零散处理，破坏分层职责。

三、本次学习目标
清晰区分 Model / DTO / VO 三者的职责边界与适用场景
掌握「Service 层作为数据转换枢纽」的标准分层写法
实现「接口层与数据层完全解耦」，数据库结构变动不影响对外接口协议
建立企业级 Go 后端项目的数据分层规范意识，为后续参数校验、多模块扩展打下基础
四、新增与改动内容明细
1. 新增目录与文件
   在项目根目录新增两个独立包，与 handler、service 同级：
   dto/：数据传输对象包，统一管理所有接口的入参结构体
   dto/user_dto.go：用户模块全部请求参数结构体（新增、更新、路径参数等）
   vo/：视图对象包，统一管理所有接口的出参结构体
   vo/user_vo.go：用户模块全部响应数据结构体（仅包含前端可见字段）
2. 各层代码改造
   Handler 层（接口控制层）
   入参全部替换为 DTO 结构体，不再直接绑定 model.User，不再使用函数内临时结构体
   返回值统一使用 VO 结构体，不再直接返回全量数据库 Model
   仅负责参数绑定与响应返回，完全感知不到数据库表结构
   Service 层（业务逻辑层）
   入参从 *model.User 调整为 DTO 结构体
   返回值从 model.User 调整为 VO 结构体
   新增核心职责：数据转换，承担「承上启下的桥梁」作用
   入站转换：DTO → Model，将前端请求组装为数据库可识别的模型
   出站转换：Model → VO，将数据库查询结果裁剪为前端可见的视图数据
   业务校验逻辑保持不变，仍在本层执行
   Repository 层（数据访问层）
   代码零改动，仍只与 model.User 打交道，完全感知不到上层 DTO/VO 的存在
   直观体现分层解耦的核心价值：上层接口协议变动，数据层无需同步修改
   Model 层
   保持不变，仅与数据库表一一对应，不参与接口数据交互
   五、新旧版本核心对比
   表格
   对比维度	基础版本（旧）	Plus 版本（新）
   Handler 入参	临时结构体 / 直接绑定 Model	统一使用 DTO 结构体
   Handler 出参	直接返回全量 Model 字段	返回裁剪后的 VO 字段
   Service 入参	接收数据库 Model	接收前端 DTO
   Service 出参	返回数据库 Model	返回视图 VO
   数据转换逻辑	无，全链路透传 Model	Service 层统一做 DTO↔Model↔VO 转换
   耦合程度	接口与数据库表强绑定	接口、业务、数据三层解耦
   数据安全性	全字段暴露，易泄露敏感信息	精准控制前端可见字段
   契约清晰度	无统一入参 / 出参契约	DTO/VO 即接口契约，集中管理
   可维护性	改表必影响接口，牵一发而动全身	各层可独立演进，改动影响范围可控
   六、项目定位与后续学习说明
   定位：本 Plus 版本是分层架构学习的进阶巩固，是基础 CRUD 项目向企业级规范升级的第一步，也是后续 Validator 参数校验、多模块扩展的前置基础。
   后续关联知识点：
   validator 参数校验：将直接基于现有 DTO 结构体扩展，属于本分层体系的配套增强
   Context、JWT、Redis 属于独立通用组件，将作为单独知识点学习，按需引入项目
