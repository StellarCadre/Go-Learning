# 依赖注入（DI）通俗讲解
> 先说最重要：**你现在这个 `learn_layer_demo‑plus‑plus`，完全不需要依赖注入，不用写，也不用纠结**。
> 你当前代码：service包的普通函数内部直接import并且调用 `repository`，属于**硬依赖**，小demo完全没问题，只是不适合大型项目、单元测试。

## 一句话定义
> **依赖注入：不要让A自己内部去new/创建它要用的B；把B在外部创建好，当作参数传给A去使用**。

- A要干活，离不开B，B就是A的**依赖**。
- 不要A自己内部 `B:=repository.xxx()`；外部造好B，传给A，这就是注入。

## 拿你现在项目对比
### 当前你的写法（无DI，硬依赖）
```go
// service包普通函数
func GetProfile(userId uint)(*vo.UserInfoVO,error){
    // 在service函数内部直接调用repository，service自己去找repo
    user,err := repository.GetUserByIdPtr(userId)
    // ...
}
```
问题：
`service` 代码**直接写死依赖repository包**。
- 想做单元测试测试service逻辑，**必须启动真实MySQL数据库**，不能模拟假数据；
- service和repository死死绑定在一起，很难替换。

> demo无所谓；企业项目要写大量单元测试的时候，这个就很难受。

### 改成最简单手动依赖注入（不使用任何第三方DI框架，Go最基础DI）
1. service不再直接import调用repository；service通过**参数接收repo实例**。
```go
type userService struct{
    // 存放外部传进来的repo
    userRepo repository.UserRepository
}

// 构造函数：外部把repo传进来，注入进去
func NewUserService(repo repository.UserRepository)*userService{
    return &userService{userRepo:repo}
}

// 业务方法，使用结构体内部已经注入好的repo，不再自己去import调用
func (s *userService)GetProfile(userId uint)(*vo.UserInfoVO,error){
    user,err := s.userRepo.GetUserByIdPtr(userId)
    // ...
}
```

2. 在main.go最顶层组装所有对象（全部在外部创建，逐层传入）
```go
//1.先造db连接
db := db.NewDB()
//2.造repo，把db注入给repo
userRepo := repository.NewUserRepository(db)
//3.造service，把repo注入给service
userSvc := service.NewUserService(userRepo)
//4.造handler，把service注入给handler
userHandler := handler.NewUserHandler(userSvc)
//5.注册路由，handler已经拿到service
r.GET("/profile", userHandler.GetProfile)
```

> 关键点：**service内部不再import repository包**！所有依赖全部从外部通过构造函数传进来，这就是手动依赖注入。

## 依赖注入最大的两个好处
### 好处1：单元测试，可以传入Mock（模拟假repo，不用真实数据库）
写service单元测试的时候，可以写一个**假的MockRepo**，不访问MySQL，直接返回伪造用户数据：
```go
// MockRepo，实现同样接口，但是不走数据库
type MockRepo struct{}
func(m *MockRepo)GetUserByIdPtr(id uint)(*model.User,error){
    //直接返回假数据，完全不碰数据库
    return &model.User{ID:1,Name:"测试用户"},nil
}

func TestGetProfile(t *testing.T){
    mockRepo := &MockRepo{}
    // 把mock实例注入给service
    svc := service.NewUserService(mockRepo)
    // 直接测试service业务逻辑，不需要启动MySQL！
    vo,err := svc.GetProfile(1)
}
```
这是企业项目DI最核心价值：**业务代码测试不依赖真实数据库、Redis**，测试跑得飞快，环境不依赖外部组件。

### 好处2：解耦，方便替换实现
未来如果要把MySQL换成内存存储、或者读写分离，只要写新的Repo实现，main组装的时候换传入的实例即可，**service一行代码不用改动**。

## 分清两个概念，很多人混淆
1. **手动依赖注入**：只用构造函数传参，不需要任何第三方库，Go项目最常用。上面例子就是。
2. **DI容器框架（wire、dig、fx）**：大型项目依赖太多，手动组装main代码太长，用工具自动生成组装代码，属于进阶工具，初学不要碰。

## 回到你的学习节奏
1. ✅现在demo阶段，完全不用DI，就用现在普通包函数写法：`service.GetProfile()`，可读性好，适合理解分层。
2. 搞懂gin分层、JWT、DTO/VO、handler‑service‑repository流程后。
3. 下一步再学习：**接口 + 手动构造函数注入**，学习单元测试mock。
4. 大型项目再考虑wire这类DI工具。

> 当初demo里面那个奇怪全局`var UserService = new(userService)`，就是作者想提前往DI方向铺垫，但是没有注入任何依赖，结构体是空，属于半成品，反而造成阅读迷惑。

## 简单总结
- 没有DI：A内部直接创建/调用B，两者绑死；测试必须要真实B。
- 有DI：外部造好B，传给A使用；A只定义需要什么，不负责创建B；测试时可以传假的Mock‑B。
- **DI主要服务单元测试与大型项目；小demo完全没必要上。**
